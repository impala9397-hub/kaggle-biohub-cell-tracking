# spec.md — kaggle-biohub-cell-tracking

Design document for this repository. Written before the code and docs, per the workspace rule
(what and why → how → tasks).

## 1. What and why

**What.** A curated, English, portfolio-quality release of our solution to the Kaggle competition
[Biohub – Cell Tracking During Development](https://www.kaggle.com/competitions/biohub-cell-tracking-during-development)
(August–September 2026). Final result: silver medal, 130th of 3,947 teams (final standings, private LB 0.92649).

**Why.** The working repository behind the result is private and messy: hundreds of experiments, working notes in
Korean, infrastructure scripts, competition data. A reviewer (for example a hiring manager) should be able to read
this repository and, within five minutes, know:

1. the problem and the metric;
2. the final pipeline and what we added on top of the public notebooks, with the leaderboard effect of each change;
3. the result, public and private;
4. the main lesson (offline validation preferred our own coordinate head; the 29 % public leaderboard did not, and
   the private leaderboard sided with the offline evidence).

Depth (method details, the full submission table, the error budget, the lessons) lives in `docs/`.

**Non-goals.**

- Not a one-command reproduction of every experiment. The offline replay harness depends on competition data and
  is not released.
- No competition data, no derived data, no model weights (see §2).
- No third-party notebooks vendored. They are referenced by URL; the base notebook is downloaded by
  `kaggle/fetch_base946.sh`.

## 2. Constraints

| Constraint | Rule |
|---|---|
| Visibility | The GitHub repository stays **private**. The owner decides on publication after reviewing it. |
| Competition data | Never committed: images, frames, ground truth, validation replays, captured features, run folders, scratch outputs. The rules (§2.4.b) forbid redistributing competition data. |
| Weights | Never committed. Our tertiary detector and coordinate heads were trained on competition data; they live in private Kaggle datasets that are named, not shipped. |
| Third-party code | Only code we wrote. Code we ported verbatim from public Apache-2.0 notebooks stays inside our patch modules, with attribution in `NOTICE` after the license was checked on the source page. |
| Language | English everywhere, including comments inside generated notebook code. |
| Personal data and secrets | No e-mail addresses, absolute home paths, cloud volume or pod ids, Drive ids, tokens. Scanned before every push. |
| Facts | Every number is taken from the working repository's records or from the Kaggle CLI / pages, not re-derived from memory. |

## 3. How

### 3.1 Layout

```text
README.md              5-minute overview: problem, result, pipeline figure, what we added, what failed, lessons
spec.md                this file
LICENSE                MIT (our code)
NOTICE                 third-party code and weights we build on, with the license seen on each source page
licenses/Apache-2.0.txt full Apache License 2.0 text, for the code ported from public Apache-2.0 notebooks
pyproject.toml         uv project for the tests and figure scripts
docs/
  method.md            each component, with figures
  results.md           public vs private for the important submissions
  lessons.md           what the leaderboard taught us
  kaggle_writeup.md    draft of the Kaggle solution write-up (not posted)
  figures/             pipeline.svg + charts (generated by scripts/)
  data/submissions.csv curated submission metadata (public and private scores), from the Kaggle CLI
kaggle/                notebook build system and patch modules (flat directory: modules chain-load siblings)
  README.md            how a kernel is built from the public base notebook
  build_r946.py        builder: base notebook + patches + knobs -> kernel directory
  build_recipe.py      named recipes (S57 … final) -> build_r946 environment
  recipes.json         the recipes, as data
  fetch_base946.sh     downloads version 4 of the public base notebook and checks its hash
  *_946.py             patch modules (tertiary detector, division gate, relink bonus, x138 port, V1284 head, …)
coordhead/
  train_coordhead.py   training of our own coordinate-regression head (pairs, by-movie CV, final fit)
scripts/
  make_figures.py      charts in docs/figures from docs/data/submissions.csv and recorded numbers
  make_pipeline_svg.py pipeline diagram
  plotnn/make_arch_figures.py  PlotNeuralNet-style architecture figures (needs a PlotNeuralNet clone + LaTeX)
tests/                 CPU tests; synthetic ones always run, builder tests skip without the base notebook
```

### 3.2 Build flow (what a reader can run)

1. `kaggle/fetch_base946.sh` downloads version 4 of the public base notebook and checks the code cell SHA-256.
   (`kaggle kernels pull` cannot return an older version; see `kaggle/README.md`.)
2. `python kaggle/build_recipe.py final-headavg-pmax8 out/` writes `out/notebook.ipynb` and
   `out/kernel-metadata.json`.
3. `kaggle kernels push -p out/` runs it on Kaggle. Only the owner can attach the private weight datasets.

### 3.3 Verification

- **Code import.** Each patch module is compared with its working-repository original by an AST check: identical
  code; only Korean comment and docstring text and `kaggle/lane-r/` paths may differ.
- **Builds.** Key recipes are built with the original and the new code. The generated notebooks may differ only in
  lines that held Korean text or old paths.
- **Tests.** `uv run pytest` on CPU. Synthetic tests need no data; builder tests need the public base notebook.
- **Rebuild check.** The final kernels are rebuilt from a fresh download of the base notebook and compared with the
  submitted kernels (`kaggle kernels pull`, owner only): only comments, docstrings, file paths and ids may differ.
- **Figures.** Every SVG and chart is rendered and inspected (no overlapping or clipped labels).
- **Scans.** `detect-secrets` plus a fixed grep list before every push.
